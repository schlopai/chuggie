# versus — a Street Fighter–style 1v1 fighter

> *A Street Fighter-style 1v1 fighter: frame data, hitboxes, motion commands and best-of-three rounds, with no entity system in the loop.*

<img src="preview.gif" alt="preview" width="480">

Four fighters, best of three, ninety-nine seconds a round. Frame data, hitboxes and hurtboxes,
blocking that depends on where you are blocking, motion specials, cancels, hit-stop and a CPU that
plays through the same input ring you do.

```bash
npm run build && npm start
```

## Controls

| | |
|---|---|
| **B** / **A** | light punch / heavy punch |
| **R** / **L** | light kick / heavy kick |
| **A + B** | throw — unblockable, close range |
| **←** (away) | block, while their attack is out |
| **↓** | crouch. ↓ + a button is a low; the heavy is a sweep |
| **↑** | jump. ↑← / ↑→ to move through the air |
| **→ →** / **← ←** | dash / back dash. The back dash is invulnerable as it leaves; the forward dash can be cancelled straight into an attack |
| **↓ ↘ →** + **A** | special. Each character also has a second one on **L** that costs meter |
| **START** | advance a screen · **SELECT** | frame-time overlay |

The heavy kick is an **overhead**: it has to be blocked standing, so it beats a crouching turtle.
The sweep is a **low**: it has to be blocked crouching. That pair is the whole guessing game, and
neither of them is code — they are one column of the table in `src/chars.tish`.

**Combos.** Any light connects into any heavier button and into either special, so `B → A → ↓↘→+A`
and `↓B → ↓L` both work with no special case anywhere — it is one bitmask per move. Damage scales
down as the string gets longer (`SCALE` in `packages/fighter.tish`), which is why a ten-hit combo is
stylish rather than a round-winner.

## What is where

| file | what it is |
|---|---|
| `packages/fighter.tish` | the character engine: states, frame data, hitboxes, pushback, cancels |
| `packages/motion.tish` | the input history ring and the command recogniser (QCF/QCB/DP/…) |
| `src/chars.tish` | the roster — four characters as a table of numbers, not four files |
| `src/main.tish` | boot, the mode machine, the round/match flow |
| `src/stage.tish` | the arena, and a long note about why it is not a banded background |
| `src/hud.tish` | health tracks, clock, pips, meters, combo counter |
| `src/ai.tish` | the CPU opponent |
| `src/frames.tish` | generated by `scripts/gen_versus.py` — the sheet's cell layout |

Rebuild the art with `npm run assets` after downloading the source packs (see
`assets/ATTRIBUTION.md`); everything is CC0.

## The three things this example is actually about

**1. A fighting game is a table.** Startup, active, recovery, damage, hitstun, blockstun, pushback,
hit-stop, and which moves this one may cancel into — nine numbers per move, nine moves per
character. `packages/fighter.tish` is the machine that reads them and contains no character-specific
code at all, which is why a fifth fighter is a call to `define` rather than a file.

**2. There is no entity system in the loop.** Every other world-shaped example here mounts
components and calls `step()`. This one runs `fighterTick(); fighterDraw(); frame()`. The engine's
`behave()` hooks dispatch through a boxed `Value` trampoline at roughly 42 ticks a callback, and a
fighter has two state machines, two hitboxes, two hurtboxes and a push-out to evaluate every frame
before the game gets to spend anything on presentation.

**3. Calls are the budget, not arithmetic.** Measured on this ROM against a 4,389-tick 60fps frame:
a one-argument call into a function that touches module state costs about **117 Timer2 ticks**,
whether or not it crosses a module boundary — it is a boxed `Value` dispatch. A function that
touches no module state at all is promoted to a real Rust fn and costs about **1**. A module-array
read costs about **1.7**, so the data plane is nearly free and the call plane is everything.

The fight loop started at 19,700 ticks on its worst frame and is now around 9,800, and essentially
all of that came from *counting calls* — asking the pad one question instead of four, reading two
packed words instead of eleven fighter fields, and not asking at all on the frames where nothing
happened. See `motionFrame`, `fighterAiView`, `fighterHudView`, and the note on the first line of
`tryStart`.

There is a fourth, smaller one that cost an afternoon: **the ARM7TDMI has no divide instruction.**
`% RING` in the input ring's index compiled to a call into a software division routine and made
`motionRead` cost 1,400 ticks. The ring is a power of two now and the index is a mask.

## Testing input headlessly

`scripts/screenshot.sh`'s key schedule counts DISPLAY frames, and this game runs under 60fps when
things are busy — so a two-frame tap can land inside a single game frame and simply not exist. A
double tap written as `255:left,257:,259:left` produced one frame of input in the ring and no dash;
`255:left,262:,269:left` produces the dash every time. When an input test fails, suspect the
schedule before the code, and dump the ring (`motionDebug`) rather than guessing.

## Two things the select screen will teach you again

`ui_clear_rect` snaps out to whole 8x8 tiles, so on a 59px pitch clearing one cell's cursor region
eats the neighbour's border — clear all four, then draw the one. And the last box has to *fit*: one
pixel past x=239 and its right edge is silently missing, which looks like exactly the same bug.

See [docs/perf-rules.md](../../docs/perf-rules.md) for the general list — this example is one of the
two it was written from.

## Known limits

The fight still overruns on its busiest frames — a hit landing with a spark, a shake and a health
bar repaint on the same frame is about two frames' work. It degrades as a dropped frame, which is
what the stage being an ordinary background rather than a banded one buys; see `src/stage.tish` for
what it looked like when it did not.
